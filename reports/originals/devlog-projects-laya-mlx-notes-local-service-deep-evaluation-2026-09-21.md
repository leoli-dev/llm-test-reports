# Laya 本地服务深度测评

**测试时间：** 2026-09-21（Asia/Shanghai）  
**被测对象：** `http://127.0.0.1:4002/v1/systemone`  
**模型：** `aac6fef/laya-multilingual-mlx`，GPU FP16，最大上下文 1024 tokens  
**机器：** Apple M5 Max，128 GB unified memory，Darwin 27.0.0，Python 3.12.13  
**范围声明：** 这是对本地 `laya-mlx` HTTP 服务的直接请求测评，**没有经过 Pi 或 pi-laya，也没有测试 Pi 的工具或 skill**。

## 结论摘要

这个服务的优点是**短请求很快、输出数值确定、越界会明确拒绝**；缺点是**并发接入架构存在硬断崖，且通用判断质量与语义鲁棒性不足**。

| 维度 | 结论 | 关键证据 |
|---|---|---|
| 单请求延时 | 优秀 | 短 state、1 个 noul 问题 P50 **4.08 ms**，P95 **4.33 ms** |
| 低并发吞吐 | 良好 | 并发 4 时 160/160 成功，约 **269 req/s**；延时随排队近线性增长 |
| 高并发可靠性 | 不合格 | 并发 5、6 稳定；并发 7 三轮都只成功 **7/64（10.9%）**，出现 reset/broken pipe |
| 上下文 | 边界可靠、容量偏小 | 三种题型都可精确用到 **1024 tokens**，再多 1 个测试单位即 422；可用 state 长度受题目前缀影响 |
| 判断准确性 | 不足 | 72 题手工合成集 **37/72（51.4%）**；低/中/高为 58.3% / 54.2% / 41.7% |
| 题型能力 | score 明显最弱 | noul 58.3%，choice 58.3%，score **37.5%** |
| 数值确定性 | 优秀 | 同一 3 题 payload 重放 60 次，60/60 成功，答案 JSON 只有 1 种 |
| 语义可靠性 | 较差 | 等价改写标签一致率 80%，概率跨度 0.378–0.951；choice 选项全排列仅 62.5% 正确 |
| 置信度可信度 | 较差 | 置信度 ≥0.9 的样本准确率仍只有 **58.1%** |

**总评：** 可以把它视为一个延时很低的“小型判别器”，但不能把它当成通用推理模型。若任务是固定 schema、窄领域、可用独立标注集校准，并且错误可复核，它有工程价值；若任务涉及否定、时序、例外、多步规则或高风险决策，目前不应直接使用。服务也不应在没有队列/限流的情况下承接并发流量。

## 1. 测试方法

### 1.1 请求路径与预热

- 所有测试均直接调用 loopback HTTP endpoint；未经过任何代理、agent 或工具层。
- 主测试前执行 10 次 warmup，模型权重保持常驻。
- 端到端延时从客户端发出请求到完整 JSON 返回；服务返回的 `local_metadata.inference_ms` 另作纯服务推理观测。
- 高并发测试使用同步起跑的独立客户端请求，以观察突发接入能力；这比均匀到达更严格。
- 主测试批次耗时约 12.46 秒；并发边界、重试、随机上下文延时和缓存权重启动另行复测。

### 1.2 准确性样本

准确性集包含 72 个手工标注的合成案例：

- 3 种输出：`noul`（是/否）、`choice`（四选一为主）、`score`（五档）。
- 3 个难度：低、中、高。
- 每个“题型 × 难度”单元 8 题，共 9 个单元。
- 英文 46 题、中文 26 题。
- 高难度覆盖否定、例外、先后状态、冲突证据和多步规则。

这是一组针对弱点的诊断集，不是来自真实生产分布的统计抽样。因此它足以揭示失败模式，但不能给出模型在某个具体业务上的最终准确率；上线前仍需独立、足量、人工复核的领域保留集。

## 2. 延时与吞吐

### 2.1 短请求并发

单请求包含短 state 和 1 个 noul 问题；每档 160 个请求。

| 同时客户端 | 成功/总数 | 成功率 | 成功吞吐 | P50 | P95 | P99 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 160/160 | 100% | 233.5 req/s | 4.08 ms | 4.33 ms | 4.44 ms |
| 2 | 160/160 | 100% | 267.7 req/s | 7.38 ms | 7.54 ms | 7.69 ms |
| 4 | 160/160 | 100% | 269.0 req/s | 14.77 ms | 14.97 ms | 15.11 ms |
| 8 | 8/160 | 5.0% | — | 17.69 ms* | 23.04 ms* | 23.08 ms* |
| 16 | 5/160 | 3.1% | — | 39.02 ms* | 45.64 ms* | 46.18 ms* |
| 32 | 8/160 | 5.0% | — | 17.86 ms* | 23.23 ms* | 23.26 ms* |

\* 失败档的分位数只统计少量成功请求，不能代表整体服务延时；失败请求主要是 connection reset、broken pipe 和本地 socket error。

1、2、4 并发时吞吐在约 269 req/s 封顶，同时 P50 大致按 1×、2×、4×增长。这说明核心推理是串行的，增加客户端并没有增加模型执行并行度，只是在排队。

每请求改为 8 个问题、每档 96 个请求后，结论相同：并发 1/2/4 均为 96/96 成功，P50 分别为 5.60/10.48/20.99 ms；并发 8/16/32 都只成功 7/96。由此可排除“只在单问题 payload 出现”的偶发现象。

### 2.2 并发断崖定位

为定位边界，对 5–8 并发各重复 3 轮，每轮 64 个短请求：

| 同时客户端 | 三轮成功情况 | 典型 P50 | 判断 |
|---:|---|---:|---|
| 5 | 64/64、64/64、64/64 | 18.0–19.8 ms | 稳定 |
| 6 | 64/64、64/64、64/64 | 21.4–21.5 ms | 稳定 |
| 7 | 7/64、7/64、7/64 | 15.5–15.7 ms* | 稳定复现断崖 |
| 8 | 6/64、7/64、7/64 | 13.9–15.8 ms* | 大量连接失败 |

根因与实现高度吻合：`local_server.py:5,91` 使用单线程 Python `HTTPServer`，注释也明确 GPU inference 在主线程串行。默认 listen backlog 很小；当 7 个连接同步冲入时，尚未被 accept 的连接被内核拒绝或重置。这不是模型变慢，而是**HTTP 接入层在模型开始处理前就丢请求**。

客户端最多重试 6 次、5 ms 指数退避后：并发 8 为 98/100 成功，并发 16 为 90/100，并发 32 为 75/100；P99 分别升至 70.2、130.4、180.7 ms。重试只能缓解，无法代替服务端有界队列和过载响应。

### 2.3 长 state 与批量问题

随机交错执行 50 次/档的单 noul 请求，避免按长度顺序带来的热身偏差：

| `alpha` state 单位 | P50 端到端 | P95 端到端 | P50 inference |
|---:|---:|---:|---:|
| 50 | 4.13 ms | 10.49 ms | 3.67 ms |
| 250 | 5.72 ms | 26.31 ms | 5.13 ms |
| 500 | 7.48 ms | 8.09 ms | 6.80 ms |
| 750 | 10.10 ms | 10.69 ms | 9.23 ms |
| 950 | 11.50 ms | 12.04 ms | 10.56 ms |
| 990 | 11.59 ms | 12.18 ms | 10.64 ms |

50 和 250 单位档出现少量系统抖动，所以 P95 不单调；中位数随输入长度平滑增长。约 900 单位的近满 context 下：

| 每请求问题数 | 成功 | P50 | P95 | P50 inference |
|---:|---:|---:|---:|---:|
| 1 | 30/30 | 13.22 ms | 14.02 ms | 12.30 ms |
| 8 | 30/30 | 60.31 ms | 62.71 ms | 59.31 ms |
| 32 | 30/30 | 250.05 ms | 260.07 ms | 248.57 ms |

问题数扩展接近线性；32 题曾出现约 482 ms 的 P99 离群点。服务契约允许 1–64 题：64 个短问题返回 200，约 29.07 ms；65 个问题正确返回 422。

### 2.4 启动时间

在临时端口启动两个相同进程，从 spawn 到 `/health` 就绪分别为 **1.867 秒**和 **1.510 秒**。这是权重已在本机缓存后的启动时间，不包含首次下载。临时进程均按 PID 停止，4002 原服务随后仍通过健康检查。

## 3. 上下文长度支持

`/health` 报告 `max_context_tokens: 1024`。服务会把 state token 与每道问题的格式化前缀一起预算；不会静默截断 state。二分查找得到：

| 问题类型 | 最大可接受 `alpha` 单位 | 接受请求实际输入 tokens | 首个拒绝单位 | 拒绝行为 |
|---|---:|---:|---:|---|
| 短 noul | 992 | 1024 | 993 | HTTP 422 |
| 4 项 choice | 996 | 1024 | 997 | HTTP 422 |
| 5 档 score | 983 | 1024 | 984 | HTTP 422 |

错误正文为 `State exceeds model context after question formatting; shorten the input`。三个题型都证明 1024 边界可真正使用，且超界是显式失败；不过“state 最多能写多少”不是固定数字，因为问题、选项和 instruction 会占用不同 token。调用方应提前留预算，不能只按字符数裁剪。

## 4. 判断准确性

### 4.1 按难度

| 难度 | 正确/总数 | 准确率 | 正确标签平均概率 |
|---|---:|---:|---:|
| 低 | 14/24 | 58.3% | 0.598 |
| 中 | 13/24 | 54.2% | 0.525 |
| 高 | 10/24 | 41.7% | 0.410 |
| **总体** | **37/72** | **51.4%** | **0.511** |

难度上升时表现下降，尤其高难 choice 只有 2/8。低难度也只有 58.3%，说明问题不只是“推理不够深”，基础否定和 score 映射同样不稳。

### 4.2 按题型与难度

| 题型 | 低 | 中 | 高 | 总体 |
|---|---:|---:|---:|---:|
| noul | 75.0% | 37.5% | 62.5% | 14/24（58.3%） |
| choice | 75.0% | 75.0% | 25.0% | 14/24（58.3%） |
| score | 25.0% | 50.0% | 37.5% | 9/24（37.5%） |

score 是最明显短板：输出容易收缩到中间档，连语义明显的低风险或高风险案例也会错。choice 在简单分类尚可，但规则一多就出现强烈的首项/表面词偏置。

英文为 24/46（52.2%），中文为 13/26（50.0%）。两者接近不代表语言等价，因为样本量小、题目没有逐条翻译配对；本轮只能说没有观察到巨大的中英文鸿沟。

### 4.3 典型失败

- **否定漏读：** `No files were deleted.` 被高置信度判断为“删除过”；`备份尚未完成。` 被高置信度判断为“已完成”。
- **当前状态被早期事件覆盖：** 主节点失败但副本已接管并服务流量，仍判断“当前不可用”。
- **例外量词失败：** “Every request passed except one health probe” 被判断为“所有请求都通过”。
- **规则/顺序偏置：** 高难 choice 对第一选项 `alpha` 有明显偏好。
- **score 中档坍缩：** 对应极低/极高的证据也常输出中间分数 1。

## 5. 可靠性与校准

### 5.1 数值确定性与批处理一致性

- 同一 3 题 payload 重复 60 次：60/60 成功，答案 JSON 完全相同。
- 同样的 noul、choice、score 分别单独请求与放在同一 batch，请求结果逐项完全一致。

因此，同一输入与同一 batch shape 下，服务有很好的数值确定性；这与仓库现有的 MLX/upstream parity 结果一致。但“重复得到同一个答案”不等于“答案正确”。

### 5.2 等价改写敏感性

同一事实“第一次付款失败、重试成功”，使用 5 个语义等价的英文问法：4/5 输出 yes，标签一致率 80%；`p(yes)` 从 **0.3782** 到 **0.9505**。其中一个问法跨过 0.5 决策边界，且概率振幅达到 0.5723。

这意味着服务适合固定模板，不适合让最终用户自由措辞后直接把概率当作可信度。

### 5.3 choice 选项顺序敏感性

将同一 4 选 1 问题的选项做 24 种全排列，正确答案 `billing` 只命中 **15/24（62.5%）**；模型还输出过 `sales` 和 `other`。`p(billing)` 范围为 **0.2682–0.6670**。语义未变，仅选项顺序变化就足以改变标签。

这是严重的决策可靠性问题。若上线使用 choice，应至少进行稳定排序、位置随机化评测，或多排列投票；更根本的方案是用目标领域数据重新训练/校准。

### 5.4 置信度不能作为安全阀

| 置信度阈值 | 覆盖率 | 阈值内准确率 |
|---:|---:|---:|
| ≥0.6 | 86.1% | 56.5% |
| ≥0.8 | 68.1% | 59.2% |
| ≥0.9 | 43.1% | 58.1% |

提高阈值并未显著提高准确率；≥0.9 甚至略低于 ≥0.8。可见这些概率在本轮分布外推理集上校准很差，不能未经领域校准就用作自动放行或高风险决策依据。

## 6. 与仓库既有 benchmark 的关系

仓库 `BENCHMARKS.md` 的既有结果提供了两类重要但不同的证据：

- 在 Apple M3 Max 上，`laya-multilingual` MLX FP16 的直接 runtime benchmark 为：短输入 1 题 P50/P95 7.39/7.79 ms，10 题 27.39/28.02 ms，50 题 127.56/142.77 ms；满 1024 context 的 1/10 题 P50 为 37.63/389.49 ms。
- 256 条 AG News 样本准确率 94.53%，并与 upstream 256/256 一致；但文档明确说明 AG News 出现在 upstream training mix 中，所以这更接近窄域分类能力和端口保真验证，不能推导出通用推理准确率。
- FP16 权重为 614 MiB；1 个短问题峰值 687.6 MiB，10 个满 context 问题峰值 1501.7 MiB。
- 对真实 checkpoint 的 63 题 parity 中，FP16 与 upstream argmax 63/63 一致，最大校准概率误差 0.0012887；100 次重复 active memory growth 为 0。

本轮 HTTP 结果与上述“运行时很快、端口数值稳定”相符，同时补上了既有 benchmark 没有回答的部分：**服务接入层高并发会失败，且模型在分布外、多步、否定与顺序变化下不可靠。** 两组结果并不矛盾；它们分别测量实现保真/窄域分类与更开放的语义泛化。

## 7. 建议的使用边界

可以考虑使用：

- 固定模板、固定 label schema 的窄域分类。
- 有真实业务保留集、可量化验收阈值，并允许人工复核或规则兜底。
- 低并发本机流水线，或者前面已有单消费者有界队列。
- 把模型概率当排序特征之一，而不是未经校准的“可信度”。

不建议直接使用：

- 否定、例外、时序冲突、多步政策规则等通用判断。
- 安全、财务、医疗、权限等高风险自动决策。
- 用户自由输入的 prompt，尤其 choice 选项顺序会变化的场景。
- 7 个或更多连接可能同时突发、且不允许失败的服务。

## 8. 修复优先级

1. **先修并发接入：** 使用 threaded acceptor 接收/校验请求，再交给单独的有界串行 inference worker；队列满时返回 429/503 和 `Retry-After`。不要让多个线程同时进入 MLX GPU 推理。
2. **建立真实领域保留集：** 分语言、题型、难度和业务损失加权；记录 confusion matrix、召回、Brier/ECE 与 selective risk。
3. **处理语义敏感性：** 固定 prompt；对 choice 做全排列一致性回归；修正否定、例外和 score 中档坍缩。
4. **再做长时稳定性：** 15–60 分钟恒定到达率与突发混合 soak，同时记录 queue wait、RSS/unified memory、MLX peak/cache memory 和系统热压力。

## 9. 限制与可复现证据

- 本轮是单机、单模型、单精度、单次测试窗口；不代表其他 Mac 或首次下载体验。
- 高并发是同步突发，不是 Poisson/恒定到达率；它刻意测试最坏接入边界。
- 准确性集只有 72 条合成样本，足以发现弱点，不能替代生产领域 benchmark。
- 本轮未做长时间热稳定性、功耗、温度或独立 GPU unified-memory 峰值测量。
- 测试时原始 JSON 写入 `/tmp/laya_service_eval_results.json` 与 `/tmp/laya_service_followup_results.json`；`/tmp` 非持久存储，本报告保留关键汇总。服务实现证据见 `$HOME/Code/laya-mlx/local_server.py:1-95`，既有性能/保真证据见 `$HOME/Code/laya-mlx/BENCHMARKS.md`。

测试结束后，PID 19317 的 4002 服务继续运行，`/health` 返回 `status: ok`、GPU、1024-token context。
