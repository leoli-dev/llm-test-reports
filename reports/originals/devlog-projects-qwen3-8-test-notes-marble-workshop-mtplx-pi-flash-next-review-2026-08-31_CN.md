## 标准基准任务（原文）

```text
制作一个 3D “Marble Workshop”：

- 用户点击“投放”后，从顶部落下一颗弹珠；弹珠会经过斜坡、环、风扇和弹簧板，最终落入不同颜色的收集槽。
- 使用真实物理碰撞；用户可拖动障碍物、暂停/继续、重置场景。
- 右侧面板实时显示：已投放数量、各颜色得分、当前 FPS。
- 每种收集槽触发不同的视觉反馈；不能依赖预录视频或 GIF。
- 页面首次打开要有 10 秒自动演示。
- 给出至少 3 个自动化验证：投放、暂停、重置。
```

## 代码审查

### P1 — 失败的物理路径被转换为看似真实的箱子得分

只有初始 `binAt(pos)` 分支（`src/sim/world.js:239-244`）证明了弹珠进入了真实的箱子体积。随后的松散托盘分支将任何在 y=3.4 以下、且已行驶足够距离的未跟踪弹珠映射到合成的 y=1.6 箱子测试**或最近的箱子**（`src/sim/world.js:263-272`）。最终的看门狗将缓慢、长距离或 14 秒的弹珠直接映射到 `nearestBin`（`src/sim/world.js:284-289`）。`src/game.js:287-315` 故意将 `collect` 和 `settle` 在得分、HUD、吐司通知、托盘灯和庆祝效果上视为相同。

这在项目自己的 `scripts/trace.mjs` 中是可观察到的：24 个通道结果中有 3 个是 `settle`，但测试套件报告所有弹珠均已被收集。物理回归测试通过接受 `scripts/physics-drain.test.mjs:131-132` 中的 `/^(collect|settle)/` 将漏洞制度化。滞留或在托盘中逃逸的弹珠必须保持视觉上未解决（或通过真实物理几何体返回），而不是基于邻近性分配分数。将自动恢复更改为物理返回滑槽/传送器，并明确标记为此类，或将其报告为无得分的失败；然后使默认通道和人群测试仅要求传感器 `collect` 事件。跟踪为 MW-01（历史本机文件，未随本报告发布）。

### P2 — 首次运行演示在手动发射器通道之外投放

手动投放使用 `course.spawn.xRange`，其值为 `[-11.3, -9.9]`（`src/game.js:115-126`，`src/sim/course.js:342`）。而每次计划内的演示投放则提供从 -1.5 到 1.4 的 x 值（`src/demo.js:9-23`）。实时新页面证据证实了 `DROP #1 x=-1.20`。这些球仍然从顶部 y 坐标开始，但绕过了实际的喷口/入口通道，因此演示无法可靠地展示所需的斜坡/圆环/风扇/弹簧序列。应从文档记录的生成范围生成演示 x 值，并添加一项测试，确保每个演示投放在得分之前都注册了 `run` 和 `finale` 路线部件。记录为 MW-02（历史本机文件，未随本报告发布）。

### P2 — 宣传的 Q/E 障碍物旋转没有处理程序

HUD 显示 `Q/E 旋转`（`src/ui/hud.js`，在实时 DOM 中渲染），但 `src/main.js:219-246` 中的完整键盘分发器没有 `q` 或 `e` 分支，且 `world.js` 未暴露任何障碍物旋转操作。要么实现安全的旋转（包括碰撞体和视觉四元数更新），要么移除该说明。记录为 MW-03（历史本机文件，未随本报告发布）。

### P2 — 新页面日志中出现可避免的 Three 警告

位于 `src/view/scene.js:22-23` 的 `PCFSoftShadowMap` 已被安装的 Three 版本弃用。位于 `src/view/scene.js:94-99` 的 `UnrealBloomPass` 在其当前参数下会发出两条 sigma 采样裁剪警告。这两者均不阻碍任务，但对于视觉基准测试而言，干净的验证基线至关重要。请使用未弃用的阴影贴图选项，并为安装的 Three 版本调整/限制泛光内核。记录为 MW-04（历史本机文件，未随本报告发布）。

### P2 — 没有静态 lint 门禁

`package.json` 包含构建、物理、浏览器和组合验证脚本，但没有 `lint` 脚本或 linter 依赖项。源代码可读且模块化，但可复现的审查应至少包含一个配置好的静态 lint 命令。记录为 MW-05（历史本机文件，未随本报告发布）。

## 积极发现

- 对于紧凑的视觉任务而言，该架构具有异常高的可审查性：`src/sim` 独立于 Three，`src/game.js` 负责编排，`src/view` 负责网格/特效，`src/ui/hud.js` 负责 DOM。
- 120 Hz 固定步长模拟、显式弹珠/刚体清理、确定性重放测试、20 弹珠人群测试以及指针拾取探针，使回归测试具体化，而非视觉猜测。
- `src/view/fx.js` 中的五种收集器反应确实各不相同且是程序化的（例如：深红冲击/火焰、蔚蓝碎片、金色光束/硬币、琥珀色尘埃、紫色内爆）；未使用预录媒体。
- 面向用户的体验连贯一致：右侧分数/状态面板、物理玻璃机器、受控的光晕以及暂停/重置/拖拽操作组合良好。高/低质量控件（DPR、AA、阴影、合成器和粒子数量）与渲染负载相匹配。

## 建议的收尾工作

1. 首先解决 MW-01，并使分数证据能够区分真实的传感器收集与任何可见的恢复机制；在禁止 `settle` 的情况下重新运行 24 车道和人群测试套件。
2. 将演示球放回实际的喷口范围内，并验证其路线部件覆盖情况（MW-02）。
3. 修正 Q/E 契约，移除 Three 警告，并添加 `npm run lint`。
4. 重新运行 `npm run verify`，然后重复新页面演示以及直接的 UI 投放/暂停/重置检查。干净的 MW-01 修复将使产品进入通过范围。
